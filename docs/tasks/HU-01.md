# HU-01 — User Login

## User Story
As an active user (ADMIN, CLIENT, or TECHNICIAN), I want to sign in with my email and password so I can access the system using my assigned role.

## Goal
Implement **backend login only**, using the existing Express, Prisma, and User model from TASK-01. Keep it simple and easy to explain.

## Scope
1. Add `POST /api/auth/login` accepting JSON `{ "email": "...", "password": "..." }`.
2. Find the user by email with Prisma and verify the password against the existing password hash using the same hashing library used by the administrator seed.
3. Reject nonexistent users, incorrect passwords, and inactive users. Use a generic `401` response for invalid credentials; do not reveal which field was wrong.
4. On success, return HTTP `200` with a signed **access JWT** and basic user information (`id`, `name`, `email`, `role`). Never return `passwordHash`.
5. Include the user's `id` and `role` in the JWT payload. Configure a short expiration (for example, 15 minutes) and read the signing secret from `JWT_SECRET` in `.env`.
6. Add `JWT_SECRET` to `.env.example` and explain how to configure it in `backend/README.md`. Do not commit a real secret.
7. Add a small set of meaningful tests for successful login, invalid credentials, and inactive users, using the existing testing approach where possible.
8. Create `docs/implementation/HU-01.md` explaining what was implemented, why, important files, verification, and limitations.

## Constraints
- **Backend only**: do not implement Angular login screens yet.
- Do not implement refresh tokens, refresh sessions, logout, protected-route middleware, registration, password reset, or user management. Those belong to later stories.
- Reuse the existing backend structure and dependencies where appropriate.
- Use JavaScript ESM, Express, Prisma, `dotenv/config`, and `process.env` directly. No Zod or extra architectural layers.
- Keep validation minimal: ensure email and password are present and strings; return `400` for malformed requests.
- Never log passwords or JWT secrets.
- Do not make Git commits or push changes without explicit approval.

## API Example
Request:
```http
POST /api/auth/login
Content-Type: application/json

{"email":"admin@example.test","password":"your-password"}
```

Success response (shape):
```json
{
  "accessToken": "<signed-jwt>",
  "user": {
    "id": "<uuid>",
    "name": "Initial Administrator",
    "email": "admin@example.test",
    "role": "ADMIN"
  }
}
```

## Acceptance Criteria
- An active seeded administrator can log in with the correct credentials.
- The endpoint returns `401` for invalid credentials or an inactive user.
- The endpoint returns `400` for missing or invalid field types.
- The access token is signed, expires, and contains the user's ID and role.
- No password hash or secret is returned.
- The README and implementation summary are updated, and relevant tests pass.
