# HU-02 — Refresh Access Token

## User story

As an authenticated user, I want to obtain a new access token without entering my credentials again, so that I can continue using the application after my access token expires.

## Scope

Implement refresh-token issuance during login and an endpoint to renew access tokens. Reuse the existing `RefreshSession` Prisma model and the authentication conventions introduced in HU-01.

## Requirements

1. On successful `POST /api/auth/login`, return an `accessToken`, a `refreshToken`, and the existing `user` object. Preserve the current response fields.
2. Generate a cryptographically random, opaque refresh token using Node.js `crypto`. Store **only its hash** in `RefreshSession`, linked to the user, with an expiration date.
3. Add `POST /api/auth/refresh`, accepting `{ "refreshToken": "..." }` in the JSON request body.
4. If the refresh token is valid, unexpired, not revoked, and belongs to an active user, return a new `accessToken` and a new `refreshToken`.
5. Rotate refresh tokens: revoke the used refresh session and store the replacement. A previously used refresh token must not work again. Keep the revoke/create operations atomic using a simple Prisma transaction.
6. Return `400 Bad Request` when `refreshToken` is missing or is not a string; return `401 Unauthorized` for invalid, expired, revoked, or reused tokens, or inactive users. Do not reveal which condition caused rejection.
7. Keep JWT payload and expiration conventions consistent with HU-01. Configure refresh-token lifetime using one straightforward environment variable, such as `REFRESH_TOKEN_EXPIRES_DAYS=7`.
8. Use the existing routes/controllers organization. Add only the code required for this story; do not introduce services, repositories, validation frameworks, or unrelated endpoints.
9. Do not implement logout, frontend integration, automatic token refresh middleware, or session-management screens in this story.

## Acceptance criteria

- Login still works and additionally returns a refresh token.
- A valid refresh token can be exchanged for new access and refresh tokens.
- The original refresh token cannot be reused after successful renewal.
- Missing or malformed input is rejected with HTTP 400.
- Invalid, expired, revoked, or reused tokens are rejected with HTTP 401.
- The database stores only refresh-token hashes, never plaintext refresh tokens.
- Existing login behavior and tests continue to work.
- A few focused automated tests cover successful renewal and rejection of invalid/reused tokens.
- `backend/README.md` is updated only if setup or configuration instructions change.
- `docs/implementation/HU-02.md` explains what was implemented, why, important files, verification, and limitations, following `AGENTS.md`.

## Manual verification

1. Log in as the seeded administrator and copy the returned `refreshToken`.
2. Send `POST /api/auth/refresh` with `{ "refreshToken": "<token>" }` and verify HTTP 200 plus both new tokens.
3. Repeat the request using the original refresh token and verify HTTP 401.
4. Use the new refresh token and verify that renewal succeeds.
5. Try a missing token and a random token; verify HTTP 400 and 401 respectively.
