# HU-04 — Create Users as Administrator

## User story

As an administrator, I want to create user accounts so that clients and technicians can access the support ticket system.

## Scope

Implement an authenticated, administrator-only endpoint to create users. Reuse the existing JWT authentication, Prisma `User` model, password hashing approach, and backend conventions.

## Endpoint

`POST /api/users`

Request body:

```json
{
  "name": "Example User",
  "email": "user@example.com",
  "password": "ExamplePassword123!",
  "role": "CLIENT"
}
```

The `role` must be `CLIENT` or `TECHNICIAN`. Administrator accounts are not created through this endpoint; the initial administrator is created by the seed script.

## Acceptance criteria

1. Requests require a valid access token in the `Authorization: Bearer <token>` header.
2. Only users with the `ADMIN` role may create accounts.
3. Validate that `name`, `email`, `password`, and `role` are provided and have appropriate types. Reject unsupported roles. Keep validation simple; do not add a validation library.
4. Normalize email consistently (trim and lowercase) and reject duplicate email addresses.
5. Hash passwords using the existing project's password hashing approach; never store plaintext passwords.
6. Create the user with Prisma, using the existing `User` model and its defaults.
7. On success, return `201 Created` with the new user's `id`, `name`, `email`, `role`, and `isActive`. Never return `passwordHash`.
8. Use clear HTTP responses: `400` for invalid input, `401` for missing/invalid/expired access tokens, `403` for authenticated non-admin users, and `409` for duplicate email addresses.
9. Preserve the behavior of existing login, refresh, and logout endpoints.
10. Add a small set of meaningful tests for the principal success and failure cases.

## Implementation guidelines

- Follow the root `AGENTS.md`.
- Reuse existing code and conventions before creating new helpers or middleware.
- Keep routes separate from controllers, consistent with HU-01.
- A small reusable authentication/role middleware is acceptable if needed; avoid additional architectural layers.
- Use JavaScript ESM, Express, and Prisma. Do not introduce TypeScript or unnecessary dependencies.
- Do not create database tables or migrations unless the existing schema demonstrably requires a change.
- Do not implement public registration, user listing, user deactivation, profile editing, email invitations, or frontend screens.

## Verification

- Admin access token + valid data -> `201` and a user record without a password hash in the response.
- No token or invalid token -> `401`.
- Client/technician access token -> `403`.
- Duplicate email -> `409`.
- Invalid/missing fields or `ADMIN` as requested role -> `400`.
- Confirm the newly created user can log in with their credentials.

Do not commit or push changes until the user approves the implementation.
