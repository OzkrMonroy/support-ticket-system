# HU-09 — Update Support Tickets

## User story
As an authorized user, I want to update permitted ticket fields or advance a ticket through its workflow so that support requests remain accurate and can be completed.

## Context
- Follow `AGENTS.md`, the existing Express/Prisma/JavaScript ESM conventions, and approved HU-07/HU-08 behavior.
- Ticket statuses: `OPEN`, `IN_PROGRESS`, `RESOLVED`, `CLOSED`.
- Ticket priorities: `LOW`, `MEDIUM`, `HIGH`.
- Ticket assignment remains outside this story (EP-03). Do not add assignment or self-assignment endpoints.

## Endpoint
- Implement `PATCH /api/tickets/:id`, requiring an authenticated, active user.
- Accept a partial JSON body containing only `title`, `description`, `priority`, and/or `status`.
- Require at least one supplied field. Reject unknown fields and invalid values using the existing Zod validation/error conventions.
- Validate `:id` as a UUID using the existing request-validation approach.
- Reuse the existing ticket representation for successful responses; return the updated ticket with HTTP 200. Do not expose credentials or other sensitive user data.

## Authorization and update rules

### CLIENT
- May update only tickets they created.
- While the ticket is `OPEN`, may edit `title`, `description`, and `priority` using the same field constraints as ticket creation. May not change its status at this stage.
- When their ticket is `RESOLVED`, may change **only** `status` to `CLOSED`.
- May not update a ticket in `IN_PROGRESS` or `CLOSED`.
- When a CLIENT attempts to close their own ticket (`status: CLOSED`) whose persisted current status is not `RESOLVED` (including `CLOSED`), return HTTP `403` with the following body. Apply no changes, including for mixed content/status requests. Missing or inaccessible tickets still return `404`; request validation and all existing business rules remain unchanged.

```json
{
  "message": "Clients can only close resolved tickets."
}
```

### TECHNICIAN
- May update only tickets assigned to them (`assignedToId` equals authenticated user ID).
- May change **only** `status`, with transitions `OPEN` -> `IN_PROGRESS` and `IN_PROGRESS` -> `RESOLVED`.
- May not edit title, description, priority, or assignment.
- No self-assignment and no access to unassigned tickets in this story. Technician updates may be unavailable until EP-03 creates assignments; retain tests using appropriately assigned fixtures.

### ADMIN
- May edit `title`, `description`, and `priority` on any ticket while it is not `CLOSED`, using existing creation field constraints.
- May perform the normal status transitions `OPEN` -> `IN_PROGRESS` -> `RESOLVED` -> `CLOSED`.
- Additionally, may set `status` to `CLOSED` directly from `OPEN` or `IN_PROGRESS` (for duplicate, mistaken, or unnecessary requests).
- May not reopen a `CLOSED` ticket or edit its fields.
- May not modify `assignedToId` in this story.

## General rules
- `CLOSED` is terminal for every role.
- Reject invalid or unauthorized field changes; never silently ignore them or partially apply a mixed invalid request.
- If a request changes both content fields and status, validate the entire operation against the **persisted starting status** and the relevant role rules before updating. For example, a client cannot edit content and close a resolved ticket in one request.
- Do not allow status jumps other than the explicitly permitted admin direct-close cases.
- Treat missing tickets and tickets outside the user's visibility as `404`, consistent with HU-08; do not reveal their existence.
- For a visible ticket, use `403` for forbidden actions or state transitions. Keep errors consistent with the existing API conventions; malformed bodies/UUIDs use existing `400` validation handling.
- Preserve `createdById`, `assignedToId`, `createdAt`, and all other immutable/system-managed fields. `updatedAt` remains Prisma-managed.
- Use focused authorization and transition logic; avoid a new permissions framework, new database models, audit logs, queue publishing, or unrelated refactors.

## Acceptance scenarios
1. CLIENT edits title/description/priority on their own `OPEN` ticket; persisted fields change.
2. CLIENT closes their own `RESOLVED` ticket; status becomes `CLOSED`.
3. CLIENT cannot change status of an `OPEN` ticket, edit a non-`OPEN` ticket, or change another user's ticket.
4. Assigned TECHNICIAN advances `OPEN` -> `IN_PROGRESS` -> `RESOLVED`, but cannot modify content or unassigned/other tickets.
5. ADMIN edits an eligible ticket, performs normal transitions, and can close directly from `OPEN` or `IN_PROGRESS`.
6. All roles are blocked from modifying `CLOSED` tickets; no reopening.
7. Invalid transitions, unauthorized fields, unknown fields, empty payloads, malformed UUIDs, and invalid content/priority are rejected without changing the ticket.
8. Missing/inaccessible tickets return `404`; unauthenticated/inactive users are rejected by existing auth middleware.
9. Existing HU-07/HU-08 tests remain passing.
