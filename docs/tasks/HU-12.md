# HU-12 — Asynchronous Ticket Email Notifications

## User story
As a ticket creator or assigned technician, I want to receive email notifications about important ticket events so that I can follow progress without repeatedly checking the application.

## Scope
Implement the project's second RabbitMQ asynchronous job: transactional email notifications using a dedicated notification queue and worker, Nodemailer, and Gmail SMTP. Reuse existing Express/JavaScript ESM, Prisma, RabbitMQ and configuration conventions. Keep the implementation minimal; do not introduce a notification management UI or job-status API (HU-13).

## Events and recipients
| Event | Trigger | Recipient |
| --- | --- | --- |
| `TICKET_CREATED` | Successful ticket creation | Ticket creator |
| `TICKET_ASSIGNED` | Successful first assignment by HU-11 worker | Assigned technician |
| `TICKET_RESOLVED` | Actual transition into `RESOLVED` | Ticket creator |
| `TICKET_CLOSED` | Actual transition into `CLOSED` | Ticket creator |

These events must reflect committed, successful business operations. Do not notify for rejected requests, unchanged status values, duplicate assignment messages, or other no-op operations. Admin-created tickets notify their actual creator. Existing role/state rules remain unchanged.

## Behavior
1. Publish a notification job after the relevant successful database operation. For `TICKET_ASSIGNED`, publish from the existing assignment worker only after a successful assignment. Do not send SMTP email directly from HTTP handlers or the assignment worker.
2. Process jobs in a dedicated RabbitMQ notification queue with a separate worker process. Follow HU-11's durable queue, persistent message, connection and acknowledgement conventions where appropriate. Avoid disrupting the assignment queue.
3. Use Nodemailer with Gmail SMTP. Read credentials from environment variables; never commit credentials or log passwords. Document setup in `backend/.env.example` and `backend/README.md` (or existing equivalent). Suggested variables: `SMTP_HOST=smtp.gmail.com`, `SMTP_PORT=465`, `SMTP_USER`, `SMTP_APP_PASSWORD`, `EMAIL_FROM`. Treat port 465 as secure TLS. Never ask for or embed a real app password.
4. Provide four simple Spanish-language templates, each with HTML and plain-text bodies. Include the ticket ID, title, priority and relevant status; avoid including the full description or sensitive account data. Use appropriate escaping of dynamic HTML content.
5. A failed email must not undo ticket creation, assignment or status updates. Log outcomes with event name and ticket ID, but avoid secrets and unnecessary personal information.
6. Use bounded handling for transient failures (consistent with the existing RabbitMQ patterns); avoid infinite immediate redelivery. Preserve enough information in logs to diagnose terminal failures. HU-13 will define generalized job status, richer retry/failure tracking and API visibility. Do not build those features prematurely.
7. Handle redeliveries safely: avoid duplicate publication on no-op transitions and assignments. RabbitMQ delivery is at-least-once, so do not claim exactly-once email delivery; implement lightweight deduplication only if practical within existing architecture, and document remaining limitations.
8. SMTP/provider unavailability must not block normal API responses while RabbitMQ accepts notification jobs. If publishing itself fails, do not silently report that the notification was queued; follow existing error/logging conventions without reversing already-committed business operations. Document the delivery guarantee and limitations rather than introducing a full transactional outbox in HU-12.

## Acceptance criteria
- Creating a ticket queues one `TICKET_CREATED` notification addressed to the creator.
- A successful initial assignment queues one `TICKET_ASSIGNED` notification addressed to the assigned technician; duplicate/ignored assignment jobs queue none.
- Changing a ticket to `RESOLVED` queues one `TICKET_RESOLVED` notification to the creator; other edits do not.
- Changing a ticket to `CLOSED` queues one `TICKET_CLOSED` notification to the creator, whether performed by an authorized client or administrator; other edits do not.
- Email messages use Spanish HTML/text templates with safe rendering.
- Notification processing is independent of HTTP request completion and of the ticket assignment worker.
- SMTP credentials are environment-based and excluded from version control.
- Worker logs successful sends, skips and errors sufficiently for testing without exposing secrets.
- Existing authorization, workflow, soft-delete and assignment rules remain intact.

## Testing
- Unit tests for event triggering, recipient selection, no-op suppression and all four template variants.
- Worker tests using mocked SMTP/RabbitMQ for success, transient error, terminal error and acknowledgement behavior; tests must not send real email by default.
- Regression tests for ticket creation, assignment, resolve and close flows.
- Document a manual integration test with a dedicated Gmail account, RabbitMQ running, notification worker running, and test recipients. Include a scenario with the notification worker stopped and then restarted.
- Do not require real SMTP credentials to run automated tests.

## Out of scope
- Notification preference management, email inbox UI, public registration, scheduled reminders, attachments, provider switching UI, generalized job-status API, full outbox architecture and advanced retries/dead-letter monitoring (HU-13).
