# HU-07 — Create Support Tickets

## Objective
Allow authenticated CLIENT and ADMIN users to create support tickets through the backend API. This story covers ticket creation only.

## Scope
- Add a `Ticket` model and the necessary Prisma migration.
- Implement `POST /api/tickets` using the existing Express route/controller conventions.
- Reuse existing JWT authentication, current-account checks, role authorization patterns, and Zod request validation.
- Add focused tests and update relevant implementation documentation.

## Ticket data
| Field | Requirement |
| --- | --- |
| `id` | UUID primary key, generated by the database/Prisma |
| `title` | Required, non-empty string |
| `description` | Required, non-empty string |
| `priority` | Required enum: `LOW`, `MEDIUM`, `HIGH` |
| `status` | Enum: `OPEN`, `IN_PROGRESS`, `RESOLVED`, `CLOSED`; defaults to `OPEN` |
| `createdById` | Required relation to `User`; taken from authenticated user, never from request body |
| `assignedToId` | Optional relation to `User`; initially `null` |
| `createdAt` | Creation timestamp |
| `updatedAt` | Update timestamp |

Use the existing Prisma schema conventions and appropriate relations. Avoid unrelated database changes.

## API contract
**POST `/api/tickets`** — Bearer access JWT required.

Request body:
```json
{
  "title": "Cannot access email",
  "description": "The email application rejects my credentials.",
  "priority": "HIGH"
}
```

- `CLIENT` and `ADMIN` can create tickets.
- `TECHNICIAN` must receive `403 Forbidden`.
- Missing, invalid, or inactive authentication must follow existing API conventions (`401` where appropriate).
- Validate the request with Zod; reject empty or whitespace-only title/description and invalid/missing priority. Follow the existing field-error format (`400`, `message` and `errors`). Use reasonable length limits consistent with the project; do not introduce unnecessary rules.
- Do not accept client-supplied `id`, `createdById`, `assignedToId`, `status`, or timestamps. Prefer strict request validation consistent with existing schemas.
- On success return `201 Created` and the created ticket with its persisted fields. Do not expose sensitive user data.
- `status` is `OPEN`, and `assignedToId` is `null` at creation.

## Acceptance criteria
1. An active authenticated CLIENT can create a ticket with a selected priority.
2. An active authenticated ADMIN can create a ticket under the same rules.
3. A TECHNICIAN cannot create tickets.
4. An unauthenticated request cannot create tickets.
5. Invalid request fields produce the established validation response and do not create a ticket.
6. The creator is derived from the authenticated account, not the request body.
7. New tickets are persisted with `OPEN` status, no assigned technician, and timestamps.
8. Focused automated tests cover successful creation, role restriction, authentication, and invalid input.

## Out of scope
- Ticket listing, details, updates, deletion, and status transitions (HU-08 through HU-10).
- Automatic technician assignment, RabbitMQ jobs, and notifications (EP-03).
- Angular screens (EP-04).
- Additional permissions or speculative extension mechanisms.
