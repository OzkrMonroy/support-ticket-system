# HU-11 — Automatic Ticket Assignment with RabbitMQ

## Goal

As a client, I want a newly created support ticket to be assigned asynchronously to an available technician, so that work is distributed without manual intervention.

## Context

- Follow `AGENTS.md`, `docs/PROJECT.md`, `docs/ROADMAP.md`, and the existing backend implementation.
- Backend: Express with JavaScript ESM, PostgreSQL, Prisma, and RabbitMQ.
- Tickets are created in `OPEN` with `assignedToId = null`. Soft-deleted tickets have a non-null `deletedAt`.
- This story implements the **first** asynchronous job. Email notifications belong to HU-12; general job visibility, retries, and failure reporting belong to HU-13.

## Scope

1. Add a minimal RabbitMQ service to the local Docker Compose setup and document the required environment variables and startup steps in `backend/README.md`.
2. Publish a ticket-assignment message when `POST /api/tickets` successfully creates a ticket. The HTTP endpoint must not wait for assignment to finish. Preserve its existing successful response shape and authorization/validation behavior.
3. Implement a separate, runnable backend worker that consumes assignment messages and updates the ticket using Prisma.
4. Implement the assignment policy below, with focused automated tests.
5. Document the actual queue flow in `docs/ARCHITECTURE.md` and create `docs/implementation/HU-11.md`.

## Assignment policy

- Consider only users with role `TECHNICIAN` and `isActive = true` (use the actual existing field names).
- Workload for each technician is the number of assigned tickets whose status is `OPEN` or `IN_PROGRESS` and `deletedAt` is `null`.
- Select the eligible technician with the smallest workload. For a tie, use a stable deterministic ordering (e.g., user ID ascending). Do not add a round-robin mechanism.
- Assign only tickets that still exist, are not soft-deleted, and remain unassigned. Never overwrite an existing assignment.
- Assignment does not change the ticket status; it remains `OPEN`.
- If no active technicians exist, leave the ticket `OPEN` and unassigned. Treat this as an expected business outcome, not a transient failure; acknowledge the message without infinite retries. Log a concise, non-sensitive outcome.
- If the ticket was deleted or already assigned before the worker processes the message, do nothing and acknowledge it. Duplicate messages must not cause reassignment.
- Priority (`HIGH`, `MEDIUM`, `LOW`) determines the order in which **pending assignment messages** should be processed, with higher priority first. Use RabbitMQ's native message-priority support if practical, and document that priority ordering applies to messages still queued, not work already being processed. Do not claim strict global ordering under concurrency.

## Messaging and failure boundaries

- Use one clearly named durable queue and persistent messages; include only the ticket ID and the minimum data necessary for the assignment task. Obtain current ticket data from the database when processing.
- Use manual acknowledgements: acknowledge only after a successful assignment or a confirmed no-op/business outcome. Do not silently acknowledge unexpected processing failures.
- Avoid uncontrolled immediate requeue loops. Implement a minimal, bounded failure behavior appropriate to the existing codebase, and document it. HU-13 will extend retry policy and job-status visibility; do not build a full generic job framework here.
- Handle RabbitMQ connection/publishing errors explicitly. Do not return an HTTP success that falsely claims assignment has already completed. If a ticket was created but publishing fails, avoid silent loss: document and implement a small, clear handling strategy consistent with the current architecture, without introducing an outbox or distributed transaction unless separately approved.
- Prevent two concurrently processed messages from overwriting the same ticket's assignment. Keep the solution straightforward; avoid broad locking frameworks.

## API behavior

- Preserve `POST /api/tickets` response compatibility. A newly created ticket may still show `assignedToId: null` because assignment is asynchronous.
- Existing `GET /api/tickets` and `GET /api/tickets/:id` should reflect the assigned technician after processing, subject to HU-08 role visibility rules.
- Do not add new public assignment, retry, or job-status endpoints in this story.

## Acceptance criteria

1. Creating a ticket produces an assignment message and the worker assigns it to an active technician without changing its `OPEN` status.
2. The technician with the fewest non-deleted `OPEN`/`IN_PROGRESS` tickets is selected; ties are deterministic.
3. Inactive users and non-technicians are never selected.
4. With no active technicians, the ticket remains unassigned and the worker finishes the message without an infinite retry loop.
5. Deleted or already assigned tickets are not assigned again, including on duplicate delivery.
6. Priority messages still waiting in the queue are processed in `HIGH` before `MEDIUM` before `LOW` order where supported by the chosen RabbitMQ configuration; document concurrency limitations.
7. Transient broker/worker errors are not silently swallowed; the chosen bounded failure behavior is tested and documented.
8. Existing ticket creation, role authorization, ticket listing/detail, updates, and soft deletion continue to work.
9. The worker can be started locally using documented commands, and tests cover the business rules and key failure/no-op cases.

## Out of scope

- Email or other follow-up notifications (HU-12).
- Job status API, dashboard, generalized retries/dead-letter workflow (HU-13).
- Manual assignment, technician self-assignment, reassignment, advanced scheduling, skill matching, or technician availability calendars.
- Frontend implementation.
