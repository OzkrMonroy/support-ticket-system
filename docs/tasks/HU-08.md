# HU-08 — List Support Tickets and View Ticket Details

## Objective

Allow authenticated users to list and view support tickets according to their current role and ownership/assignment. This story is read-only.

## Context

- Follow `AGENTS.md`, `docs/PROJECT.md`, `docs/ROADMAP.md`, and `docs/ARCHITECTURE.md`.
- Inspect the actual `Ticket` Prisma model, the HU-07 implementation, and existing authentication/validation conventions before coding. Reuse existing field names and patterns; do not assume a different schema.
- HU-07 allows CLIENT and ADMIN to create tickets. Technician assignment is not implemented yet.

## Endpoints

### `GET /api/tickets`

Requires a valid access token and an active user.

Return tickets visible to the authenticated user:

- `ADMIN`: all tickets.
- `CLIENT`: only tickets created by that user.
- `TECHNICIAN`: only tickets assigned to that user.

Sort by `createdAt` descending; use `id` descending as a deterministic tie-breaker if needed. Return `200 OK` with a JSON array, including `[]` when there are no visible tickets. Use the established API response conventions.

### `GET /api/tickets/:id`

Requires a valid access token and an active user. Return the ticket only if the authenticated user is allowed to see it under the same rules as the list endpoint.

- Return `200 OK` for a visible ticket.
- Return `404 Not Found` for a missing ticket **or** a ticket not visible to the user; do not disclose whether an inaccessible ticket exists.
- Validate the `id` parameter using the existing Zod middleware; malformed UUIDs return the existing standardized `400` validation response.

## Response data

Return persisted ticket fields from the existing Prisma model, plus basic creator and assigned-technician information when available. For related users, expose only safe public fields (e.g. `id`, `name`, `email`, `role`), consistent with the existing API. Never expose `passwordHash`, tokens, session data, or other sensitive fields.

Use a consistent ticket representation across both endpoints. Avoid adding fields or relations solely for this story.

## Implementation guidance

- Keep visibility rules consistent across list and detail queries; a small shared helper for constructing the Prisma visibility filter is acceptable if it simplifies the code.
- Apply the visibility restriction in the database query, rather than fetching all tickets and filtering them in memory.
- Keep the existing routes/controllers and authentication patterns; avoid new authorization frameworks or abstractions.
- Do not add pagination, searching, filtering by status/priority, ticket updates, assignment, or self-assignment.
- Future possibility: technicians may eventually browse unassigned tickets and claim them. **Do not implement or grant those permissions in HU-08.** Keep today's visibility rule easy to change without designing a speculative permissions system.

## Acceptance criteria

1. ADMIN can list and view any ticket.
2. CLIENT can list and view only tickets they created.
3. TECHNICIAN can list and view only tickets assigned to them; before assignments exist, an empty list is valid.
4. A missing or unauthorized ticket detail request returns `404`.
5. Invalid ticket UUID returns the existing `400` validation error format.
6. Missing, invalid, or inactive-user authentication is rejected according to existing conventions.
7. Lists are newest-first, and no sensitive user fields are returned.
8. Existing ticket creation and authentication functionality remains unaffected.
