# HU-10 — Soft Delete Support Tickets

## User story
As an authorized user, I want to delete a support ticket so that tickets created by mistake or no longer needed are excluded from normal operations without losing their database record.

## Scope
Implement `DELETE /api/tickets/:id` using soft deletion. Keep the implementation consistent with AGENTS.md, HU-07 through HU-09, the existing Express/Prisma architecture, and established validation/error conventions.

## Business rules
- Add nullable `deletedAt` (`DateTime?`, initially `null`) to the `Ticket` model, with a Prisma migration.
- Deletion sets `deletedAt` to the current timestamp; it does not physically delete the row or change `status` to `CLOSED`.
- `CLIENT` may delete only their own tickets while the current status is `OPEN`.
- `TECHNICIAN` may not delete tickets.
- `ADMIN` may delete any non-deleted ticket regardless of status.
- Already-deleted tickets are treated as not found. Do not expose them in normal ticket reads or allow updates to them.
- A denied request must not modify any ticket fields.
- Do not implement restore, trash views, bulk deletion, or asynchronous jobs in this story.

## API contract
### `DELETE /api/tickets/:id`
Requires an authenticated, active user.
- `204 No Content`: successful soft deletion, with no response body.
- `400 Bad Request`: invalid UUID; use the existing Zod validation error shape.
- `401 Unauthorized`: missing or invalid authentication, following existing conventions.
- `403 Forbidden`: authenticated user can see the ticket but is not permitted to delete it (for example, CLIENT owns a non-OPEN ticket, or TECHNICIAN attempts to delete an assigned ticket). Follow existing authorization response conventions.
- `404 Not Found`: ticket does not exist, is already deleted, or is not visible to the caller. Do not disclose inaccessible ticket existence.

## Existing endpoint integration
- `GET /api/tickets`: exclude `deletedAt != null` for every role; preserve existing role filters and ordering.
- `GET /api/tickets/:id`: treat soft-deleted tickets as `404` for every role.
- `PATCH /api/tickets/:id`: treat soft-deleted tickets as `404`; do not modify them.
- `POST /api/tickets`: newly created tickets have `deletedAt = null`.
- Apply deletion and role visibility conditions in Prisma queries where practical; avoid retrieving all tickets and filtering in application memory.
- Preserve all previously approved role and state-transition rules.

## Implementation guidance
- Reuse existing auth, role-visibility, UUID validation, error handling, and testing patterns.
- Keep changes focused; no generic soft-delete framework, extra endpoints, or speculative abstractions.
- Use the existing Prisma migration workflow. Update architecture documentation only if the actual model change requires it.

## Acceptance criteria and tests
1. CLIENT deletes their own OPEN ticket: `204`, persisted `deletedAt` populated.
2. CLIENT cannot delete their own non-OPEN ticket: `403`, no modification.
3. CLIENT cannot delete another user's ticket: `404`, no modification.
4. TECHNICIAN cannot delete an assigned visible ticket: `403`, no modification.
5. ADMIN can delete any non-deleted ticket, including non-OPEN tickets: `204`.
6. Repeating deletion of an already-deleted ticket returns `404`.
7. Deleted tickets disappear from list results and return `404` on detail and update endpoints, regardless of role.
8. Malformed UUID returns the existing standardized `400` validation response.
9. Missing/invalid authentication follows existing `401` behavior.
10. Existing create, list, detail, and update tests remain passing.
