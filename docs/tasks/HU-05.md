# HU-05 — List and Deactivate Users

## User story

As an administrator, I want to list registered users and deactivate accounts so that I can manage access to the support ticket system.

## Scope

Implement the following backend endpoints using the existing Express, Prisma, and JWT conventions:

- `GET /api/users` — list registered users.
- `PATCH /api/users/:id/deactivate` — deactivate a user.

Both endpoints require a valid access token and the `ADMIN` role. Reuse the authentication and authorization middleware already implemented in HU-04.

## Requirements

### List users

- Return `200 OK` with a JSON array of users.
- Include `id`, `name`, `email`, `role`, and `isActive` for each user.
- Never expose `passwordHash`, refresh tokens, or other sensitive fields.
- Use a predictable order (for example, creation date).
- Do not add pagination, filtering, or searching for this story.

### Deactivate user

- Find the user by the `id` route parameter.
- Set `isActive` to `false`; do not delete the record.
- Return `200 OK` with the updated user's safe public fields.
- Return `404 Not Found` when the user does not exist.
- Repeated deactivation may return `200 OK` with the already inactive user.
- Prevent administrators from deactivating their own account through this endpoint.
- Return `403 Forbidden` for self-deactivation.

### Access control

- Requests without a valid access token return `401 Unauthorized`.
- Authenticated users without the `ADMIN` role receive `403 Forbidden`.
- An inactive account must not be able to log in or use protected endpoints, including refresh. Review existing auth behavior and make only the minimum changes necessary to enforce this requirement. Do not implement broader session management or new database tables.

## Acceptance criteria

1. An administrator can retrieve the user list without sensitive information.
2. A client or technician cannot list or deactivate users.
3. An administrator can deactivate another user's account.
4. The deactivated account cannot log in or access protected endpoints or refresh tokens.
5. Deactivation does not delete the user record.
6. Nonexistent IDs return `404`; self-deactivation is rejected.
7. Relevant automated tests pass.
