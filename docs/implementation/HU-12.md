# HU-12 — Asynchronous Ticket Email Notifications

## Status and implementation

Completed and explicitly user-approved on October 25, 2026. The user confirmed manual testing. Automated regression tests were rerun successfully before updating the roadmap. The supplied task specification is included unchanged.

- Added independent durable notification queue with confirmed persistent event snapshots, separate prefetch-1 worker and Nodemailer Gmail SMTP transport.
- Creation queues to its actual creator; successful first assignment queues to the selected technician; committed RESOLVED/CLOSED transitions queue to the creator. Existing validation, permissions, transactional state checks, soft deletion and assignment rules remain intact. Rejected/no-op operations publish nothing.
- Assignment captures its ticket snapshot and chosen technician at the successful conditional write. HTTP publication occurs after transaction completion. A failed notification publication does not prevent attempting creation's assignment job.
- SMTP is environment-configured only in the notification worker. TLS for 465 and required STARTTLS for 587, bounded connection/greeting/socket timeouts, no raw provider error logging, and no file/URL access through Nodemailer.
- Four Spanish text/HTML templates escape dynamic HTML and contain ID/title/priority/status, excluding descriptions and sensitive account data.
- Chose HU-11's minimal bounded handling: one attempt per delivery; errors, including transient SMTP errors, nack without requeue. Successful SMTP acceptance acks. No schema, outbox, job status API or generalized retry layer.

## Notification events and SMTP configuration

| Event | Trigger | Recipient |
| --- | --- | --- |
| `TICKET_CREATED` | Successful creation | Actual ticket creator, including ADMIN |
| `TICKET_ASSIGNED` | Successful first conditional assignment | Assigned technician |
| `TICKET_RESOLVED` | Actual transition into RESOLVED | Ticket creator |
| `TICKET_CLOSED` | Actual transition into CLOSED | Ticket creator |

The separate RabbitMQ notification worker uses `SMTP_HOST` (default `smtp.gmail.com`), `SMTP_PORT` (default 465, secure TLS; 587 requires STARTTLS), `SMTP_USER`, `SMTP_APP_PASSWORD` and `EMAIL_FROM`. Credentials are local environment values only; the API and assignment worker do not use SMTP. Setup and the manual checklist are in `backend/README.md`.

## Delivery guarantees and limitations

SMTP/provider downtime does not block HTTP or assignment while RabbitMQ accepts jobs. Broker publication still takes time and can fail. HTTP publication failure returns 503 with persisted ticketId; assignment notification publication failure is logged and the committed assignment is acknowledged. Do not recreate tickets or repeat transitions as recovery.

There is no atomic database/broker transaction, outbox or persistent deduplication. Commit/publish crashes, failed publication and terminal rejection can lose mail. SMTP acceptance followed by a crash before ack can duplicate email; processing is at least once, not exactly once. Accepted mail may still fail to reach an inbox. Event snapshots can outlive ticket edits/deletion and separate queues/providers do not guarantee email arrival order. Assignment replay skips assigned tickets and therefore does not recover their missing notification. Deliberate developer republishing may duplicate mail; no notification recovery API or CLI was added.

No automatic SMTP retries, dead-letter storage, worker reconnection or generalized job visibility. Restart workers after broker disconnection; HU-13 will define richer retry/status behavior. Broker access should protect stored titles and recipient addresses. Automated SMTP tests use mocks; account-specific Gmail authorization is covered by manual testing with dedicated recipients.
