# HU-02 — Refresh Access Token

## Implementation

Successful login now returns `accessToken`, `refreshToken`, and the existing basic `user` object. Each refresh token is 32 cryptographically random bytes encoded as hexadecimal. Only its SHA-256 hash is stored in the existing `RefreshSession` model, together with the user ID and expiration.

`POST /api/auth/refresh` accepts a JSON string field `refreshToken`. Valid, unexpired, unrevoked sessions belonging to active users receive a signed access JWT and a replacement refresh token. Missing, empty, or non-string input returns 400. Unknown, expired, revoked, reused tokens and inactive users share a generic 401 response. Unexpected failures receive a generic 500 response without exposing credentials.

## Decisions

The existing controller, router, Prisma model, and dependencies were reused. Small private helpers in the controller generate/hash refresh tokens and preserve HU-01 access JWT conventions: HS256, user `id` and `role`, and a 15-minute lifetime. No migration, new library, service, or repository was needed.

Refresh rotation uses a Prisma transaction. A conditional update revokes the old session only if it is still unrevoked and unexpired; the affected-row count must be one before creating the replacement. This prevents two concurrent requests from consuming the same token. If replacement creation fails, the transaction rolls back the revocation.

`REFRESH_TOKEN_EXPIRES_DAYS` defaults to seven. It accepts whole days from 1 through 36500 and rejects invalid configuration at startup. Each replacement receives a full new lifetime; existing sessions keep their original expiration.

## Verification

Executed `npm test` against the configured PostgreSQL database. The first attempt failed because PostgreSQL was unavailable and Docker Desktop was stopped. Started Docker Desktop with `open -a Docker`, then ran `docker compose --env-file backend/.env -f infrastructure/compose.yaml up -d --wait`; the existing PostgreSQL service became healthy without deleting its data volume.

Repeated `npm test`: all 14 reported tests passed, including the existing login, seed, and health checks. Refresh checks covered:

- Random token format, SHA-256 storage instead of plaintext, user linkage, and a configured two-day lifetime.
- Successful renewal, correct signed access JWT payload and 15-minute expiration, revocation of the old session, and a usable replacement.
- Rejection of the original token after renewal.
- Two simultaneous exchanges producing exactly one 200, one 401, and one replacement session.
- Generic 401 responses for unknown, expired, revoked tokens and inactive users.
- 400 responses for missing, empty, non-string tokens and malformed JSON.

Test cleanup removes only generated fixture users and their sessions, plus the specific administrator session created by the login test. Existing application users and sessions are preserved. No manual token exchange was performed; HTTP integration tests exercised the endpoints directly.

## Limitations

Logout, frontend integration, automatic refresh middleware, and session-management screens remain outside this story. Revoked and expired sessions are retained; automatic cleanup is not implemented. Rotation does not invalidate existing access JWTs or revoke every session after token reuse. The token pair must be treated as private credentials.

Tests require PostgreSQL, the existing migration, matching seeded administrator credentials, and free ports `32101`, `32102`, and `32103`. PostgreSQL was left running after verification. No Git commit or push was created.
