# HU-05 — List and Deactivate Users

## Implementation

- `GET /api/users` returns an array containing only `id`, `name`, `email`, `role`, and `isActive`, ordered by creation date and then ID.
- `PATCH /api/users/:id/deactivate` sets `isActive` to `false` and returns the same public fields. Repeated deactivation succeeds without deleting the record.
- Both endpoints reuse JWT authentication and administrator authorization. Self-deactivation returns `403`; unknown or malformed IDs return `404`.
- Authentication now checks the stored user on every protected request and uses the current database role. Missing or inactive users receive `401`, including when using previously issued access tokens.
- Login and refresh already checked active status, so their implementations were preserved.

## Decisions and important files

- `backend/src/controllers/user.controller.js`: direct Prisma queries and a shared public-field selection keep responses safe without adding services or dependencies.
- `backend/src/routes/user.routes.js`: registers the two administrator-only endpoints alongside user creation.
- `backend/src/middleware/auth.middleware.js`: checks current account status after JWT verification; database failures return `500` rather than allowing access.
- `backend/tests/users.test.js`: integration coverage for public fields and ordering, administrator permissions, deactivation, retained records, repeat requests, self-deactivation, unknown IDs, and rejection of login, refresh, and existing access tokens after deactivation.
