# HU-01 — User Login

## Implementation and decisions

Added `POST /api/auth/login` for active users of all three existing roles. The controller validates nonempty string fields, queries Prisma by email, and verifies the stored bcrypt hash. Unknown users, wrong passwords, and inactive users receive the same generic 401 response. Invalid fields and malformed JSON receive 400.

Successful login returns only `accessToken` and the user's `id`, `name`, `email`, and `role`. `jsonwebtoken` signs HS256 tokens containing `id` and `role`, with a 15-minute lifetime. `JWT_SECRET` comes directly from the environment; startup rejects a missing or blank value. Database and signing errors return a generic 500 response without logging credentials.

A small controller keeps login separate from server startup without introducing a service layer. The existing schema and bcrypt library were reused, so no migration was needed. Express's JSON parser and a small error handler provide consistent JSON errors.

## Verification

Executed `npm install jsonwebtoken` and `npm test`. All nine reported tests passed, including six login subtests: active ADMIN, CLIENT, and TECHNICIAN login; seeded administrator login; generic rejection of invalid credentials and inactive users; and malformed request validation. Token checks verified the signature, ID, role, 900-second lifetime, rejection with the wrong secret, and expiration. Exact success-response assertions exclude password hashes and other user fields. Existing seed and health tests also passed.

Tests used the configured PostgreSQL database and temporary HTTP servers on ports `32101` and `32102`. Only generated test users were removed; existing users were not modified by the login tests. The seed test preserves an existing administrator. No clean-checkout installation was repeated during this story.

## Limitations

Configure a private random `JWT_SECRET` in the local `.env` before starting the backend; tests use their own secrets. Email lookup remains exact, matching the existing seed behavior. The health endpoint does not check the database.

There are no frontend screens, protected-route middleware, refresh tokens, logout, registration, password reset, or user management. `RefreshSession` remains unused. No schema or database reset was required.

Dependency installation still reported the three existing high-severity findings in the Prisma dependency chain. Prisma was kept at the required `6.19.3`; no forced upgrade was applied.
