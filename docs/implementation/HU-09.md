# HU-09 — Update Support Tickets

Status: Completed; tested and explicitly approved by the user.

## Implementation and decisions

- Added authenticated PATCH /api/tickets/:id with existing UUID validation, current-account authentication, and strict partial Zod validation. Creation constraints are reused; at least one field is required.
- Reused the HU-08 database visibility filter and safe response relations. Missing/invisible tickets return the same 404; forbidden operations on visible tickets return 403.
- CLIENT can edit own OPEN content or close own RESOLVED tickets with status only. Assigned TECHNICIAN can advance OPEN to IN_PROGRESS and IN_PROGRESS to RESOLVED. ADMIN can edit non-CLOSED content, perform normal forward transitions, or close directly from OPEN/IN_PROGRESS. CLOSED is terminal; same-status requests are rejected.
- All fields are checked against the persisted starting status before writing. A small controller helper handles permissions without a new framework or layer. A Prisma transaction reads, conditionally updates using starting status/visibility, and returns the updated safe representation. Mixed invalid operations never partially apply. Immutable fields are excluded by strict validation; updatedAt remains Prisma-managed.
- No schema changes, migrations, dependencies, assignment API, queues, or frontend were needed.

## CLIENT close-error improvement

- For a visible, own ticket, a CLIENT request containing status CLOSED when the persisted status is OPEN, IN_PROGRESS, or CLOSED returns HTTP 403 with `{"message":"Clients can only close resolved tickets."}`. The message is selected only after the existing authorization logic rejects the operation; permissions and transitions are unchanged.
- Visibility is checked first, preserving 404 for missing/inaccessible tickets. Invalid requests retain existing validation behavior. Mixed content/close requests apply no changes. A mixed request on a RESOLVED ticket still receives the generic forbidden response; status-only closure remains allowed.
