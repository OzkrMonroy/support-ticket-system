# HU-13 — Durable asynchronous job tracking, retries and recovery

Status: manually tested and explicitly approved by the user on October 25, 2026. HU-13 and EP-03 are Completed in the roadmap. Commit authorized by the user; no push authorized.

## Implementation and decisions

- Additive AsyncJob migration: job type/event, independent status/result, consumed/max attempts, fixed safe error/skip reason, timestamps, unique eventKey, private JSON snapshot and minimal dispatch/claim fields. Ticket soft deletion preserves jobs; physical deletion cascades (also permits fixture cleanup).
- Ticket creation transaction stores assignment and TICKET_CREATED jobs. Actual RESOLVED/CLOSED transitions store their notification in the update transaction. No event exists for a rolled-back write. API still returns its persisted ticket representation; broker unavailability now leaves durable pending work instead of HTTP 503.
- Assignment retains HU-11 least-load/ID tie-break and conditional OPEN assignment. The worker transaction commits assignment, its distinct TICKET_ASSIGNED notification and job completion atomically. Duplicate/no-longer-eligible work completes as SKIPPED; no technicians is a valid skip.
- Unique ticket/event keys fit the approved workflow, where tickets cannot reopen/repeat notification transitions. Duplicate creation/delivery reuses the original job. Legacy queued HU-11/HU-12 envelopes are adopted into jobs, preserving original notification snapshots; no queue purge is used.
- Existing durable queues/options/priorities remain. Confirmed persistent envelopes contain jobId, attempt generation and ticketId. `job-queue.js` adds only durable classic TTL/dead-letter retry queues: 5000 ms after attempt one, 15000 ms after attempt two. There are three total processing attempts, not three additional retries. Scheduling state persists before publication; no sleeping/timers implement processing retries.
- Conditional claims increment attempts and assign a random token. Processing locks its row and verifies that token. Assignment effects and completion commit together; email completion commits after SMTP acceptance. A duplicate/old-generation envelope cannot consume the next retry or repeat completed work. Manual ack follows a persisted outcome; database failure before claim/outcome closes the worker connection, allowing redelivery and later recovery.
- SMTP 5xx, EAUTH/EENVELOPE/EMESSAGE and invalid persisted payloads fail permanently. SMTP 4xx, timeouts/network/database/unknown errors retry up to the bound. Only fixed safe categories are stored/logged; no raw exception, address or secret is returned.
- One-shot `jobs:dispatch` recovers claims older than 120 seconds (consumed attempts retained; exhausted claims fail), republishes PENDING deliveries older than five minutes and dispatches up to 100 unpublished rows. Confirmation precedes publication bookkeeping; uncertain confirmation may cause duplicates. Active processing locks prevent recovery from overlapping its database effects. API/workers also attempt dispatch for their own ticket.
- `GET /api/tickets/:id/jobs` returns a plain array, newest first by createdAt/id, with explicit safe selection. Existing active authentication and HU-08 visibility apply; malformed UUID 400, missing/soft-deleted/inaccessible ticket 404. No frontend/global list/manual retry endpoint added.

## Operations

From `backend/`, run `npm run prisma:generate` and `npm run prisma:deploy`, then start API and both existing worker commands. Stop old processes before upgrading; never run old/new consumers concurrently. No queue deletion/recreation or data reset is required. No new environment variables or dependencies.

After outages/restarts run `npm run jobs:dispatch`, repeating for backlogs above 100. Schedule that same command every minute with an existing OS scheduler for unattended recovery, using the backend working directory/environment. Restart workers manually after broker disconnect. The command logs safe dispatch errors; investigate these and rerun after fixing the broker. A successful process exit alone does not guarantee all jobs were dispatched. `npm run assignment:publish -- <ticket-uuid>` now persists/reuses the original assignment job and attempts ticket dispatch; it does not reset terminal jobs.

Use the authorized ticket jobs endpoint to inspect PENDING/PROCESSING/COMPLETED/FAILED, attempts and safe failure/skip reasons. FAILED is terminal; correct the cause and investigate without manually rewriting job state or repeating business operations. Full startup/configuration/upgrade/recovery instructions are in `backend/README.md`.

## Known limitations

- At-least-once delivery, not exactly once. SMTP acceptance followed by process death/database rollback can duplicate mail. SMTP acceptance is not inbox delivery; SMTP timeouts can be ambiguous.
- SMTP holds a transaction/connection/row lock, bounded by a 60-second Prisma transaction timeout. Long or interrupted provider calls may remain ambiguous. Recovery thresholds and dispatch scheduling add latency; recovered retries may wait another complete TTL interval.
- Recovery requires periodic/manual command execution; workers require manual restart after broker loss. Unpublished jobs remain pending without dispatch. A five-minute republish threshold also recovers early/duplicate deliveries that did not claim.
- Classic RabbitMQ queues/TTL dead-letter transfer are not lossless across all broker/node/storage failures. Durable PostgreSQL PENDING rows permit later republishing while database state survives. Preserve both existing volumes; permanent database loss requires backups outside this story.
- No historical event reconstruction, prior legacy attempt history, retention cleanup or automatic terminal-job replay. Adopted notifications for physically removed tickets are logged/acknowledged as not-found; normal soft deletion retains rows and committed snapshots. Event keys assume the existing non-reopening workflow.
- Priority affects queued assignment envelopes only; multiple workers can choose from concurrent workload snapshots. Email arrival order across queues is not guaranteed.
