# HU-11 — Automatic Ticket Assignment

Status: Completed — tested and explicitly approved by the user. The user authorized the commit `feat(tickets): add asynchronous ticket assignment`; no push is authorized.

## Implementation and decisions

POST ticket creation now publishes a persistent ticket-ID message to one durable RabbitMQ classic priority queue (`ticket-assignment`). It waits for publisher confirmation, never assignment, and preserves the existing 201 scalar response. A separate JavaScript ESM worker consumes with manual acknowledgements and prefetch 1.

The assignment function selects only active TECHNICIAN users, counting their non-deleted OPEN/IN_PROGRESS tickets. Lowest workload wins, with ascending user ID for ties. A conditional update requires an OPEN, non-deleted, unassigned target; it cannot overwrite another delivery's assignment. Status is preserved. Missing/deleted/already-assigned/non-OPEN tickets and no-technician outcomes finish without retry.

One small dependency, amqplib, and no Prisma changes or migrations were needed. Run one worker locally; multiple workers may select using the same workload snapshot for different tickets. Native priorities LOW=1, MEDIUM=2, HIGH=3 apply to pending messages, not delivered work or strict global order with multiple consumers.

Unexpected processing failures are logged and negatively acknowledged without requeue: no immediate loop, automatic retry, dead-letter topology or generic job framework. Such messages are discarded and require manual republishing after repair. Broker disconnection stops the worker; restart manually. HU-13 retains generalized retry/status scope.

If persistence succeeds but publishing fails, POST returns 503 with the existing ticketId and explicit instructions not to create it again. The CLI republishes by ID using current database priority. This simple strategy avoids silent publication failures without an outbox. A crash between commit and publish still requires inspection and manual recovery. An uncertain confirmation may have published successfully; duplicates are safe. No claim of atomic delivery is made.

## Remaining limits

Manual recovery and process restart are intentional HU-11 boundaries. No automatic reassignment when technicians later become available, public retry endpoint, notification, job table or job-status API is added. Full tests should run with the assignment worker stopped so prior scalar creation assertions remain deterministic. Existing creation tests leave harmless messages for fixture tickets that have been removed; normal consumption skips missing tickets. The smoke check consumed such pending messages. The README includes a manual POST/worker/GET demonstration; that complete UI-free scenario was not separately executed in this verification.

Priority configuration follows [RabbitMQ priority queue documentation](https://www.rabbitmq.com/docs/priority); confirm publishing follows the [amqplib channel API](https://amqp-node.github.io/amqplib/channel_api.html).

## Follow-up review — skip diagnostics

The worker only processes deliveries from RabbitMQ's `ticket-assignment` queue. It does not scan or periodically query for existing unassigned tickets. Each message triggers a lookup of that specific ticket and, if eligible, technician workload queries. Existing unassigned tickets without a queued message need explicit publication through the recovery CLI.

Many skipped IDs can come from durable messages accumulated while the worker was stopped, especially HTTP creation tests: those tests publish messages, then physically remove their own ticket fixtures without removing the messages. Duplicate/redelivered messages, soft deletion, existing assignments and status changes also cause skips. These are possible causes supported by the code and test lifecycle, not a diagnosis of every historical ID. Previous `skipped` logs did not record enough information to distinguish them retroactively.

The initial lookup now selects only deletedAt, assignedToId and status by ticket ID, retaining the same eligibility checks and conditional write. An optional skip callback preserves assignTicket's existing outcome strings and lets the delivery handler add a concise reason to its single outcome log:

- `not-found`: no row exists for the delivered ID.
- `soft-deleted`: the row has deletedAt set.
- `already-assigned`: the row has an assignee.
- `not-open`: the current status is not OPEN.
- `eligibility-changed`: the ticket passed the initial checks but the conditional write matched no row. The exact concurrent change is unknown; no speculative reason or extra diagnostic query is added.

When multiple initial conditions apply, reasons use the order above. Example: `Ticket assignment <uuid>: skipped (not-found)`. Logs contain only the ticket ID and a fixed reason, without ticket content or user details. The no-technician outcome remains `no-technicians`. Assignment policy, outcome strings, acknowledgements and bounded failure handling are unchanged.
